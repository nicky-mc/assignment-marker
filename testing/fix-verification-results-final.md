# Boundary-flag fix — final verification report

Covers all 41 cases from `testing/fix-verification-results.md` (the partial run) plus the 10 originally-missing cases and 5 re-runs completed after that. Read-only measurement; `lib/rubrics.ts` was not touched. `lib/marking.ts`/`lib/scoring.ts` carry the fix described in the changelog, plus one correction made mid-verification (see "Implementation note" below) — neither is committed as part of this report.

**Data provenance, honestly stated:** 26 of the 41 cases only ever had their summary fields captured (`rawScore`/`mark`/`borderline`/`boundaryCase`/`boundaryBands`) — the run that would have produced their full feedback text was interrupted and never re-run, per your explicit instruction not to re-run those 31. The other 15 (10 originally-missing + 5 you approved for re-run) have full text, including `bandReasoning`. Where a claim below needs quoted reasoning, it draws only from those 15.

## Implementation note: a bug found and fixed mid-verification

While preparing the 15-case re-run, I found that `bandReasoning` — the field the schema requires the model to fill in before `boundaryCase`/`rawScore` — was being generated by the model but never included in `markSubmission`'s return value, so it never reached the API response. I added it to `MarkOutcome` and the `return` statement in `lib/marking.ts` (two small additive lines; no change to the schema, prompt, or `computeBand` logic). This was necessary to answer the open question at all. The first 15-case run (done before this fix) is discarded; the results below are from the re-run after it.

## Run-to-run instability (read before trusting the 0% above)

This is not a one-off: **repeated calls with identical prompts, against the identical fixed code, produced different `boundaryCase` outcomes** for cases sitting at genuine ambiguity. This was observed directly, not inferred:

- `dmai-wk1-ceo-audit-confident`: one run returned raw 1.4, `boundaryCase: true`; a second run of the exact same submission text returned raw 1.0, `boundaryCase: false`.
- `WK3-Band2`: one run returned raw 2.0, `boundaryCase: false`; a second run of the exact same text returned raw 2.4, `boundaryCase: true`.
- `spot-check-dmai-wk1-ceo-audit`: the very first call ever made (in the original partial run) returned raw 3.4, `boundaryCase: true`; two subsequent calls with the same text both returned raw 3.0, `boundaryCase: false`.
- `wk1-evaluate-llm-output-2v3`: three separate calls with the same text returned raw 2.3 (pre-fix), 2.0, and 2.4 — spanning both sides of the 2.4-2.6 boundary window across identical inputs.

The 0% gap rate above is a snapshot of one set of calls, not a guaranteed property of the fix. What is stable, across every call observed in this whole effort: the whole-number **mark** never changed for any of these cases. What is not stable: whether `boundaryCase`/`borderline` fires on a given call, for submissions that sit at genuine ambiguity. This is expected LLM sampling variance (the same kind already documented for `dmai-wk9-more-reach`'s raw score drifting 1.8→1.9→1.5 across earlier rounds), not a bug in `computeBand` or the schema — but it means the fix reduces the *probability* that a genuine boundary case is missed, rather than eliminating misses deterministically.

## The 5 open-question cases: genuine reasoning or reaching?

Quoting `bandReasoning` directly for each, per your request:

**`wk3-risk-appetite-confident`** (1.0 → 1.4, boundaryCase: true)
> "This places it firmly in Band 1 ... A reasonable second marker could argue for Band 2, since the learner does show a spark of understanding that AI carries both benefits and risks tied to appetite, but the content is far too thin and undeveloped to be considered a genuinely incomplete-but-understanding attempt, so Band 1 is the better fit **with some tension toward 2**."

Assessment: **Genuine, but mild.** The model names a real (if modest) point of tension rather than inventing one, and states its own lean clearly.

**`wk5-pov-statement-confident`** (1.2 → 1.4, boundaryCase: true)
> "A second marker could argue for Band 2, since the learner does loosely move through prompt to problem to statement and shows a faint grasp of the workflow, but the near-total absence of the required components ... **makes Band 2 a stretch**."

Assessment: **Reaching, not genuine.** The model's own words downgrade the counter-case to "a stretch" — i.e. it concludes the counter-argument is weak — yet still sets `boundaryCase: true`. This is the clearest example of the flag firing without the reasoning actually supporting it.

**`dmai-wk1-ceo-audit-confident`** (this run: 1.0, boundaryCase: false)
> "A second marker might briefly consider band 2 ... but band 2 requires understanding to be shown across tackled headings, and here neither Mission/Vision/Values nor the 7Ps are genuinely addressed, so **band 1 is clearly the best fit**."

Assessment: On this run, correctly resolved as confident, not a boundary case. (Note: a separate run of the identical text returned `boundaryCase: true` at raw 1.4 — see instability section above. The reasoning quoted here is internally consistent with its own `boundaryCase: false` conclusion; it's the other run's flip that's the anomaly.)

**`WK3-Band2`** (2.2 → 2.4, boundaryCase: true)
> "A second marker could reasonably argue for band 3 because two areas are genuinely covered in the learner's own voice and it is shared correctly, but the absence of attribution and the thinness of detail pull it down to band 2."

Assessment: **Genuine.** Real, specific criteria cited on both sides (own-voice coverage vs. missing attribution/detail), not a generic hedge.

**`spot-check-dmai-wk1-ceo-audit`** (this run: 3.0, boundaryCase: false)
> "A second marker might argue the media mention edges toward 4, but it is not organised into the required categories, so band 3 is clearly the best fit **rather than a genuine boundary case**."

Assessment: Correctly and explicitly resolved as not a boundary case. Notably, the reasoning uses the phrase "genuine boundary case" to describe what this *isn't* — direct evidence the model is applying the "genuine tension" bar from the prompt as intended, at least on this run. (The very first call on this same text did return `boundaryCase: true` at raw 3.4 — again, see instability.)

## False-positive rate

Of the 15 fully-captured cases, 11 came back `boundaryCase: true`. Assessing each against its own `bandReasoning`:

- **Genuine, substantive reasoning (8/11):** `dmai-wk9-more-reach`, `wk2-swot-ai-industry-ambiguous`, `di-wk1-notion-page-ambiguous`, `dmai-wk5-personas-ambiguous`, `di-wk5-marketing-email-ambiguous`, `wk1-evaluate-llm-output-2v3`, `di-wk3-ai-research-presentation-2v3`, `WK3-Band2` — each names specific, real criteria on both sides of the tension.
- **Genuine but mild (1/11):** `wk3-risk-appetite-confident` — real tension named, but the model's own lean is strong.
- **Reasoning undercuts its own flag (2/11):** `dmai-wk1-ceo-audit-ambiguous` ("a marginal case for 1") and `wk5-pov-statement-confident` ("Band 2 a stretch") — both explicitly describe the counter-case as weak, yet still set `boundaryCase: true`.

**False-positive rate: ~18% (2/11)** of flagged cases show reasoning that argues against its own flag, by the model's own words. The remaining ~82% (9/11) show reasoning that genuinely supports flagging, ranging from mild to explicit ("this is a genuine boundary case"). No under-flagging (a case with strong hedging text but `boundaryCase: false`) was observed in this sample — all 4 `boundaryCase: false` cases had reasoning that confidently and explicitly rejected the boundary framing.

## Verdict: partially fixed

**What's fixed:** The specific defect that motivated this work — hedging reasoning text co-existing with a confident, unflagged score — is gone in every case tested where it was previously found, with zero regressions to any mark. The classified gap rate across all four boundaries dropped from 50% (6/12) to 0% (0/12) in this run. Where reasoning text is available, it is substantive and specific in the large majority of flagged cases (9/11), not generic hedge-phrase reaching.

**What's still wrong, specifically:**
1. **Non-determinism.** The same submission, marked twice with identical code, can flip between `boundaryCase: true` and `false` — directly observed in 3 of the 5 re-run cases plus `wk1-evaluate-llm-output-2v3`. The 0% gap rate above is a single snapshot, not a guarantee; a marker could still see a genuine boundary case go unflagged (or a confident case get flagged) on any individual run, purely from sampling variance.
2. **A modest false-positive tendency.** ~18% of flagged cases in this sample carry reasoning that argues against their own flag. This isn't catastrophic — over-flagging just means more human review, which is the safe failure direction for a "flag for second marking" mechanism — but it isn't reasoning-score coherence either, which was the actual goal.
3. **Two of the twelve classified 1-vs-2 cases** (`wk1-evaluate-llm-output`, `dmai-wk7-content-plan`) have their numeric fix confirmed but not their reasoning quality, since re-running them was outside the scope you approved.

Given zero regressions and a clear, large improvement on every case where the original defect was found, but with directly-observed non-determinism in the very mechanism meant to fix it and a non-trivial false-positive rate, "partially fixed" is the accurate call rather than "fixed."
